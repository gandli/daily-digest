### 重复链接 — 重发语义

当 Telegram 群里有用户再次贴出已经处理过的链接时,Bot 会按"已完成"还是"上次不完整"采取不同的回复策略。下面用一条真实会话演示完整的重发流程,帮助你判断 Bot 的行为是否符合预期。

### 步骤 1: 发送一条已处理过的链接

在群聊中直接粘贴一条此前 Bot 已经成功处理过的链接,例如 `https://example.com/blog/demo-post`。这是最常见的重发场景——常常是有人晚进群、错过了原消息,或单纯想再分享一次。Bot 会识别该链接属于已完成的存档记录,而不是当作新内容去重新抓取与总结。

### 步骤 2: 观察 Bot 的"重发"回复

Bot 检测到这是已 done 的条目后,会跳过抓取与摘要生成步骤,直接调用存档数据,回复一条 ♻️ 消息:♻️ 示例博文: 演示页 📝 这是一篇用于演示重发语义的示例文章摘要。 📁 Telegraph · <

这条消息的语义和第一次处理时一致——同样包含标题、摘要、Telgraph 与源链——但前缀从 ✅ 变成了 ♻️,明确提示用户:"这是已有的存档,不是新生成的"。这样既避免重复抓取造成对方站点压力,又让新进群的用户也能拿到完整阅读入口。

![重发语义效果:Bot 用 ♻️ 前缀复读已存档的标题、摘要与三链](assets/09-repost-r1.png)

### 步骤 3: 确认三链与预期一致

仔细对比重发消息和原消息的三链(标题、Telgraph 链接、源链接),内容应一字不差。如果出现不一致,说明存档数据可能损坏,此时可联系管理员触发人工修复。对于普通用户来说,看到 ♻️ 前缀即可放心——内容已经是稳定版本。

### 步骤 4: 理解重发的几种分支

虽然本轮会话只覆盖了 done 状态的 ♻️ 重发,但完整的重发语义还包括两个分支:

- retry(上次不完整):若原条目处于"未完成"状态(例如摘要缺失、抓取失败),Bot 会先发一条 🔁 提示,然后重新跑一次完整流程,补齐三链。
- 老记录无存档:若历史数据中没有该链接的任何存档,Bot 会按新链接处理,挂到队列里补抓取并补链。

三种分支对应三种语义前缀:♻️ 表示直接复读,🔁 表示重跑,无前缀则视为全新链接。

### 小贴士

- 看到 ♻️ 前缀不要以为是 Bug,这是 Bot 故意"复读"存档以节省抓取资源,同时让晚到群的用户也能拿到链接。
- 如果你希望强制 Bot 重抓以拿到最新内容(例如原文章有更新),可以私聊管理员触发 retry,而不是简单重发链接。
- 重发语义只在群内生效;在私聊场景下 Bot 会按新链接处理,因为私聊没有共享存档上下文。
