### 重复链接 — 重发语义

当一条链接已经被处理过，再次发送给 Bot 时，Bot 会基于历史存档直接重发标题、摘要与三链，不会重新跑整条抓取与生成链路。这种"重发语义"让重复内容在群里不浪费资源，也不产生噪音，同时保留了可追溯的语义一致性。

### 步骤 1：发送重复链接

用户把之前已经处理过的链接原样发给 Bot，例如：

`https://example.com/blog/demo-post`

Bot 立即识别到该链接在存档中存在，进入重发分支。

### 步骤 2：查看重发消息

Bot 回执以 ♻️ 图标开头，表示这是"重发已处理链接"的语义分支，而非新处理。消息体包含三个部分：

- 标题：示例博文: 演示页
- 摘要：📝 这是一篇用于演示重发语义的示例文章摘要。
- 三链：📁 Telegraph · <…>、GitHub · <…>、Notion · <…>

整条消息结构与首次处理时保持一致，只是图标换成了 ♻️，让读者一眼就能识别这是历史内容的复用，而不是新内容的产出。

### 步骤 3：理解 Bot 的判断逻辑

Bot 重发语义背后有三种判定状态：

- done：上一次处理完整成功，本次直接重发标题、摘要与三链，不重跑抓取与生成。
- retry：上一次处理不完整（例如 Telegraph 写失败、Notion 同步失败），Bot 会先提示该次为重试，再补跑缺失环节后回传。
- 老记录无存档：链接在 Bot 记忆里存在，但底层 Telegraph / GitHub / Notion 资源已不可用，Bot 会重新抓取并补链，给出一份新的三链。

用户在群里看到 ♻️，可以默认是 done；看到 🔁 则意味着 Bot 正在补完上一次未完成的工作；看到普通图标则说明是全新处理。

### 小贴士

- 重复发同一条链接不会重复占用 Bot 的抓取与生成额度，只会触发一次轻量级查询，适合在多人协作的群里"补发"漏看的人。
- 如果你看到的是 🔁 而不是 ♻️，说明上一次的存档并不完整，可以留意 Bot 是否最终回齐了三链，避免错过 retry 后的补链结果。
- 当存档资源失效时 Bot 会自动重新挂链，最终回执仍是完整三链，不必担心历史链接变成死链。
