# 重复链接 — 重发语义

当你向 Bot 重复发送一条已经处理过的链接时,Bot 会智能区分三种情况:之前已经完整处理过、上一次处理不完整、或者老记录中根本没有存档。本节按真实对话逐步说明这三种重发语义对应的 Bot 行为与你的操作。

### 步骤 1: 发送已处理过的链接(done)

把上次已经成功处理过的链接再次发给 Bot。本节示例中,用户向 Bot 发送了 `https://example.com/blog/demo-post`,这条链接此前已经走过完整的提取 → 摘要 → 补链 → 存档流程。

### 步骤 2: 接收 Bot 的 ♻️ 重发响应

Bot 不会重新抓取网页、不会重新跑提取与摘要流程,而是直接复用上次的结果,按 `♻️ 标题+摘要+三链` 的格式回给你。真实回复如下:

> ♻️ 示例博文: 演示页 📝 这是一篇用于演示重发语义的示例文章摘要。 📁 Telegraph · <

可以看到开头是 ♻️ 重发标记,而不是 ♻️ 之外的其它语义符号;标题、摘要、Telegra.ph 存档链接与源链接一次性给出,与首次处理时的内容保持一致。

### 步骤 3: 理解三种重发语义的差异

虽然本节示例只命中了 done 路径,但你要清楚另外两种情形 Bot 的行为,避免误判:

- **done(本次示例)**:直接 ♻️ 标题+摘要+三链 重发,不重跑任何流水线;
- **retry(上次不完整)**:Bot 会先回 🔁 提示,告诉你上一次处理未完成,经过确认后重跑提取与补链;
- **老记录无存档**:数据库里只有早期占位记录,没有 Telegraph 等存档,Bot 会按新流程重新挂载并补齐三链。

### 步骤 4: 核对结果并按需处理

收到 ♻️ 响应后,建议你先核对三件事:标题是否与你之前看到的一致、摘要是否仍是同一版本、📁 后的 Telegraph 链接是否仍可访问。核对无误就无需再做任何操作;若发现摘要明显陈旧或链接已失效,可手动删除该记录后重新发送,让 Bot 走一次完整的新流程。

## 小贴士

- 用 ♻️ 开头即可一眼识别 Bot 走的是「重发」而非「重跑」,响应速度通常在 1 秒内,因为完全跳过抓取与摘要。
- 若你期望 Bot 强制重跑(例如源站已更新),请先在 Bot 中删除旧记录再发链接,否则仍会命中 done 路径直接重发旧结果。
- 当 Bot 回复 🔁 而非 ♻️ 时,表示上一次处理不完整,此时按提示确认即可触发补跑,无需手动删除记录。
